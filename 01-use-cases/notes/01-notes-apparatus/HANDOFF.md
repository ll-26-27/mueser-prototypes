## 1. Context

Ben's notes arrive from everywhere: email to himself, voice memos, Markdown and Word files, highlights in PDFs, items and notes in a reference manager. He wants them in **one place**, **aggregated by project**, **tagged with themes and connections**, and, where a note belongs to two projects, **posted under both**. He wants to **review** this in a page that shows everything, not a feed.

"The notebook" (`~/Development/26/the-notebook/`) was offered as a starting point. It is the Learning Lab's planning monorepo with a small Next.js reader for folders of Markdown and two capture routes (dictation and photographed pages). It has no database, tags, projects or email handling. What is worth lifting from it: the cleanup prompt and the note frontmatter shape in `interface/nextjs/lib/dictate.mjs`, the faithful-transcription prompt in `lib/photos.mjs`, and, if a browser capture page is ever wanted, `app/components/recorder.js`. The stack here is Python, to match the rest of this repository.

Everything stays on Ben's machine. The one step that sends text out is `enrich`, which asks a model to propose summaries, projects, themes and connections; it can be turned off, and an item marked private never goes to it.

## 3. Components

### 3.1 Ingest (`python -m mueser.notes ingest --case … [--only email|voice|text|pdf|zotero]`)

Walks the inbox folders. Every file becomes one or more **items**, and its bytes are copied once to `outputs/store/raw/<sha256>.<ext>`; a file already seen (same sha256) is skipped and reported. Nothing is moved or deleted from the inbox.

| folder | formats | how | what becomes the item |
|---|---|---|---|
| `inbox/email/` | `.eml`, `.mbox` | stdlib `mailbox` and `email`; threads by `Message-ID`, `In-Reply-To`, `References`; HTML parts converted to text with the HTML kept in raw | one item per message; `captured_at` from `Date`; `people` from From/To/Cc; attachments listed with name, type and sha256, and ingested as their own items when they are `.pdf`, `.docx`, `.md` or audio |
| `inbox/voice/` | `.m4a`, `.mp3`, `.wav`, `.ogg` | transcription, **local first**: `mlx-whisper` on Apple silicon, `faster-whisper` elsewhere (`[voice]` extra), model name recorded; OpenRouter audio (the-notebook's route, Gemini) only when `--engine openrouter` is passed | one item; `captured_at` from file metadata or the filename's timestamp; the whole transcript with segment timestamps in `transcripts`; a cleanup pass (title and paragraphs, text otherwise unchanged) is a **proposal**, the raw transcript stays the item text |
| `inbox/text/` | `.md`, `.txt`, `.docx` | frontmatter honoured (`title`, `date`, `project`, `tags`); `.docx` through python-docx | one item; frontmatter `project` and `tags` enter as proposals with source `frontmatter`, auto-accepted under a rule in `rules.yml` if Ben wants that |
| `inbox/pdf/` | `.pdf` | PyMuPDF (`[pdf]` extra): highlight, underline and note annotations with page number, quoted text and the annotation's own text; document metadata | one item for the PDF, one **child item per annotation** (`kind: annotation`, parent id), so a highlight can be tagged on its own |
| `inbox/zotero/` | CSL-JSON, BibTeX, Zotero RDF; or Zotero 7's local API `http://localhost:23119/api/users/0/items` read-only when `--zotero-local` is passed | items, child notes, tags, collections | one item per Zotero item (`kind: reference`), one per note (`kind: note`, parent); Zotero tags enter as proposals with source `zotero`; collections map to projects through `projects.yml` aliases |

Every item keeps its text **whole**. No field is truncated; a very long email is a very long row.

### 3.2 Enrich (`python -m mueser.notes enrich --case … [--since …] [--no-model] [--model …]`)

One pass per item that has no proposals yet from the current prompt hash. Deterministic parts first, for every item: a candidate list of **connections** (items sharing a thread, an attachment, a person, a Zotero key, or three or more content words after stopword removal), and `projects` matched by alias or code in subject, filename or frontmatter. Then, unless `--no-model` or the item is `private`, the model (OpenRouter, prompt `src/mueser/notes/prompts/enrich.md`, strict JSON schema, temperature 0) returns:

```json
{"summary": "two sentences", "projects": [{"id": "weimar-letters", "confidence": 0.8, "why": "…"}],
 "proposed_projects": [{"name": "…", "why": "…"}],
 "themes": [{"id": "censorship", "confidence": 0.7}], "proposed_themes": [{"name": "…", "why": "…"}],
 "entities": {"people": [], "places": [], "works": []},
 "connections": [{"item_id": "…", "why": "one line"}]}
```

`projects` and `themes` must come from the controlled lists given in the prompt; anything else goes under `proposed_*`. `connections` are ranked **only among the deterministic candidates** given in the prompt; the model cannot invent an id. Every field lands in `proposals` with `status: proposed`, the model, the prompt hash and the cache key. A proposal becomes a **tag** only when accepted in the viewer (an event in the log), or when a rule in `inputs/config/rules.yml` accepts it and the rule's id is written in the record.

### 3.3 Build (`python -m mueser.notes build --case …`) and serve (`python -m mueser.notes serve --case … [--who ben] [--port 8766]`)

`build` reads the database and the log and writes `outputs/index.html`: one self-contained file with the data in a `<script type="application/json">` blob and the client inline, so it opens from disk. Views:

- **Projects:** one column or page per project with every item whose project tag is accepted; an item under two projects appears under both (the "double posting").
- **Themes:** the same by theme.
- **Timeline:** items by `captured_at`, filterable by source and project.
- **People:** who appears where.
- **Review queue:** every `proposed` proposal grouped by item, with accept, reject and (for `proposed_*`) merge-into-existing; keyboard-friendly.
- **Item page:** the whole raw text, source path and sha256, the transcript with timestamps for voice, the parent for annotations and Zotero notes, accepted tags, proposals, connections with their reasons, and the item's own history from the log.
- **Search:** client-side over titles, text and tags.

Review actions are events in `outputs/store/log.jsonl`, written exactly as in the reading room: `evt_<uuid4>`, localStorage first, POST to `/api/log` when served, export to `outputs/inbox/` and `notes log ingest` otherwise. `notes apply` reads the log and sets proposal statuses and tags in the database; the log, not the database, is the record. `build` after `apply` shows the new state. `serve` serves the repository root as the reading room's does, so the top bar's links work, and refuses dotfiles.

### 3.4 Export (`python -m mueser.notes export --case … --project <id> [--since …] --out outputs/exports/`)

A Markdown file per project with every accepted item in full (title, date, source, whole text, accepted themes, connections), in date order, with a table of contents. A file that holds summaries instead of items is named `<project>-summary.md` and says so in its first line.

## 4. Data model (SQLite, `outputs/store/notes.sqlite`)

```sql
items(id TEXT PK,             -- sha256 of the raw bytes, or sha256(parent_id || locator) for children
      kind TEXT,              -- email | voice | text | pdf | annotation | reference | note
      source_type TEXT, source_path TEXT, raw_path TEXT, sha256 TEXT,
      parent_id TEXT NULL, thread_id TEXT NULL,
      captured_at TEXT, ingested_at TEXT,
      title TEXT, text TEXT,  -- whole; never truncated
      language TEXT NULL, private INTEGER DEFAULT 0, meta JSON)
people(item_id, role, name, address)
transcripts(item_id, engine, model, text, segments JSON, raw JSON, created_at)
proposals(id PK, item_id, kind,       -- summary | project | theme | proposed_project | proposed_theme | entity | connection | cleanup
          value TEXT, target_id TEXT NULL, confidence REAL, why TEXT,
          source TEXT,                 -- model | frontmatter | zotero | rule:<id>
          model TEXT, prompt_sha256 TEXT, cache_key TEXT, created_at TEXT,
          status TEXT,                 -- proposed | accepted | rejected | merged
          decided_by TEXT, decided_at TEXT, decision_event TEXT)
tags(item_id, kind, value)             -- derived from accepted proposals by `apply`; rebuilt, never hand-edited
connections(a_id, b_id, why, status, decision_event)
runs(run_id, command, params JSON, counts JSON, cost_usd, started_at, finished_at)
```

Log event (`outputs/store/log.jsonl`), the reading-room shape with this project's bodies:

```json
{"id": "evt_…", "ts": "…", "who": "ben", "client": "mueser.notes@<git sha>", "build_id": "…",
 "type": "accept | reject | merge | tag | untag | note | status",
 "target": {"item_id": "…", "proposal_id": "…"},
 "body": {"into": "existing-theme-id", "text": "…"}}
```

## 7. Conventions

- The raw file is copied once and never modified; the item text is whole.
- Derived text (transcript, cleanup, summary) carries engine or model, prompt hash and cache key.
- Everything a model says is a proposal until accepted in the log or by a named rule.
- The log is append-only and is the record; the database is derived from ingest plus the log and can be rebuilt.
- `private` items never go to a model; `--no-model` sends nothing.
- `inputs/inbox/`, `outputs/store/`, `outputs/exports/`, `outputs/inbox/` and `*.sqlite` are not committed. Fixtures are synthetic and named `synth-*`.
- Python 3.12, `uv`, `typer`, `pydantic`, `ruff`, `pytest`; SQLite through the standard library.
